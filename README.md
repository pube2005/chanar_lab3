## 3. Service Level Objective (SLO)

| Сценарио | SLI (хэмжих үзүүлэлт) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency | p95 < 50 ms | 20 VU, 1 минут |
| Reliability | /pay error rate | < 8% | 20 VU, 1 минут |
| Availability | Нийт хүсэлтийн амжилтын хувь | ≥ 90% | 20 VU, 2 минут, 10 секундийн зогсолт |
| Recovery | Серверийн сэргэх хугацаа | ≤ 12 секунд | Chaos туршилт |
| Report performance | /report latency | p95 < 450 ms | 20 VU, 1 минут |

### 3.1. Босго сонгосон үндэслэл

- **Performance:** /cart/add нь зориудын хүлээлтгүй энгийн endpoint тул 50 мс-ийн босго сонгосон.
- **Reliability:** /pay endpoint-д 5%-ийн санамсаргүй алдаа загварчилсан тул хэлбэлзлийг харгалзан 8%-ийн босго сонгосон.
- **Availability:** 120 секундийн туршилтад 10 секундийн зогсолт оруулахаар төлөвлөсөн тул 90%-ийн босго сонгосон.
- **Recovery:** 10 секундийн зогсолт болон сервер дахин асахад 2 секундийн нэмэлт хугацаа тооцож, 12 секундийн босго сонгосон.
- **Report performance:** /report endpoint нь 200–400 мс-ийн зориудын хүлээлттэй тул нэмэлт боловсруулалтын хугацааг харгалзан 450 мс-ийн босго сонгосон.

Эдгээр босго нь урьдчилан тодорхойлсон зорилтот утгууд бөгөөд бодит туршилтаар баталгаажуулна.

### 3.2. Error Budget тооцоо

**Availability SLO:** 90%

**Хэмжилтийн цонх:** 120 секунд

Зөвшөөрөгдөх алдааны хувь:

`100% - 90% = 10%`

Хугацаанд суурилсан Error Budget:

`120 × 0.10 = 12 секунд`

Төлөвлөсөн зогсолт:

`10 секунд`

Зогсолтын дараах үлдэх хугацааны төсөв:

`12 - 10 = 2 секунд`

Иймээс хугацаанд суурилсан загвараар систем 120 секундийн хугацаанд хамгийн ихдээ 12 секунд ажиллахгүй байх боломжтой.

Хүсэлтэд суурилсан Error Budget:

`Error Budget = Нийт хүсэлтийн тоо × 0.10`

Бодит availability:

`Availability (%) = (Амжилттай хүсэлт / Нийт хүсэлт) × 100`

Хүсэлтэд суурилсан бодит Error Budget болон availability-г Chaos туршилтын дараа тооцно. Хугацаанд суурилсан болон хүсэлтэд суурилсан хэмжүүрүүд заавал ижил үр дүн өгөхгүй.

## 5. Mini Chaos Engineering туршилт

### 5.1. Туршилтын нөхцөл

- Virtual Users: 20 VU
- Duration: 2 минут
- Төлөвлөсөн серверийн зогсолт: 10 секунд

- Сүүлийн холболтын алдаа: 14:25:50
- Алдаа бүртгэгдсэн хугацаа: 23 секунд
- Exit code: 99

Туршилтын явцад серверийг зориудаар зогсоож, дахин асаасан. k6 тайланд Request Failed болон connectex алдаа бүртгэгдсэн.

### 5.4. Availability болон Error Budget

Availability = (4372 / 5865) × 100 ≈ 74.54%

Зөвшөөрөгдөх алдааны хувь = 100% - 90% = 10%

Хүсэлтэд суурилсан Error Budget:

- 5865 × 0.10 = 586.5
- Зөвшөөрөгдөх хамгийн их бүхэл алдаатай хүсэлт: 586
- Бодит алдаатай хүсэлт: 1493
- Төсөв хэтэрсэн хүсэлт: 1493 - 586 = 907
- Error Budget ашиглалт: (1493 / 586.5) × 100 ≈ 254.56%

Хугацаанд суурилсан Error Budget:

- 120 × 0.10 = 12 секунд
- Холболтын алдаа бүртгэгдсэн хугацаа: 23 секунд
- Төсвийн ойролцоох хэтрэлт: 23 - 12 = 11 секунд

Эхний болон сүүлийн холболтын алдааны цагийн зөрүүгээр доголдлын хугацааг үнэлсэн. Яг сэргэсэн мөчийг тусад нь хэмжээгүй тул 23 секунд нь recovery time-ийн ойролцоо үнэлгээ юм.

### 5.5. Туршилтын шинжилгээ

Chaos туршилтаар Availability 98.55%-аас 74.54% болж буурсан. Payment error rate 4.32%-аас 27.82% болж өссөн. Үүний улмаас Availability болон Reliability threshold FAIL болж, k6 exit code 99 буцаасан.

Сервер ажиллахгүй үед хүсэлтүүд хурдан алдаа буцааснаар throughput өсөж, average latency буурсан байна. Энэ нь системийн гүйцэтгэл сайжирсан гэсэн үг биш.

Хугацаанд суурилсан болон хүсэлтэд суурилсан Error Budget нь өөр өөр хэмжүүр юм. Сервер ажиллахгүй үед iteration хурдан дуусаж, хүсэлтийн давтамж нэмэгдсэнээр хүсэлтэд суурилсан төсөв илүү их зарцуулагдсан.

Payment error rate нь төлбөрийн дотоод алдаа болон холболтын алдааг хамтад нь хэмжсэн. Цаашид HTTP 500 алдаа болон connection error-ийг тусдаа SLI болгон хэмжих шаардлагатай. Мөн latency-г зөвхөн амжилттай хүсэлтүүдээр нэмэлтээр хэмжих нь илүү бодитой үнэлгээ өгнө.
