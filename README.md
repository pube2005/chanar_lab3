## 3. SLO ба Error Budget

| Сценарио | SLI | SLO | Цонх |
|---|---|---|---|
| Cart | p95 latency | < 50 ms | 1 мин, 20 VU |
| Payment | Error rate | < 8% | 1 мин, 20 VU |
| Availability | Амжилттай хүсэлтийн хувь | ≥ 90% | 2 мин, 20 VU |
| Report | p95 latency | < 450 ms | 1 мин, 20 VU |

### Босго сонгосон үндэслэл

- **Cart:** Локал серверийн хариу хугацаа бага тул 50 мс-ийн босго сонгосон.
- **Payment:** Серверт 5% санамсаргүй алдаа үүсгэдэг тул 8%-ийн босго сонгосон.
- **Availability:** Богино хугацааны доголдлыг зөвшөөрөх зорилгоор 90% сонгосон.
- **Report:** Сервер 200–400 мс хүлээлттэй тул 450 мс-ийн босго сонгосон.

### Error Budget

- Туршилтын хугацаа: 120 секунд
- Зөвшөөрөгдөх алдааны хувь: 100% − 90% = 10%
- Хугацааны Error Budget: 120 × 0.10 = **12 секунд**

### k6 Threshold

```javascript
thresholds: {
    'http_req_duration{name:cart}': ['p(95)<50'],
    'http_req_failed{name:pay}': ['rate<0.08'],
    'checks': ['rate>=0.90'],
    'http_req_duration{name:report}': ['p(95)<450'],
}
```

### 4.1. PASS туршилт

### 4.2. Chaos туршилт

Серверийг зориудаар зогсоож, дахин асаах үед Availability болон Reliability threshold FAIL болсон.

- Төлөвлөсөн зогсолт: 10 секунд
- Эхний холболтын алдаа: 14:25:27
- Сүүлийн холболтын алдаа: 14:25:50
- Алдаа бүртгэгдсэн хугацаа: 23 секунд

Бодит Availability:

```text
4372 / 5865 × 100 ≈ 74.54%
```

Хүсэлтэд суурилсан Error Budget:

```text
Зөвшөөрөгдөх алдаа = 5865 × 0.10 = 586.5
Зөвшөөрөгдөх бүхэл хүсэлт = 586
Бодит алдаа = 1493
Хэтэрсэн хүсэлт = 1493 - 586 = 907
Budget ашиглалт = 1493 / 586.5 × 100 ≈ 254.56%
```

Холболтын алдаа бүртгэгдсэн 23 секунд нь 12 секундийн хугацааны төсвөөс давсан. Гэхдээ серверийн яг сэргэсэн мөчийг хэмжээгүй тул recovery time-ийг нарийвчлан тогтоогоогүй.

Сервер зогссон үед хүсэлтүүд хурдан алдаа буцааснаар хүсэлтийн давтамж нэмэгдсэн. Иймээс хугацаанд болон хүсэлтэд суурилсан Error Budget ялгаатай үр дүнтэй гарсан.

Payment error rate нь холболтын болон төлбөрийн дотоод алдааг хамтад нь хэмжсэн тул цаашид эдгээрийг тусдаа SLI болгон хэмжих шаардлагатай.

### 4.3. Зориуд FAIL туршилт

Үндсэн SLO-г өөрчлөхгүйгээр `slo-test-fail.js` файлд Report threshold-ийг зориудаар хатууруулсан.

```javascript
'http_req_duration{name:report}': ['p(95)<100']
```

- Threshold: p95 < 100 ms
- Бодит p95: 398.39 ms
- Хэтрэлт: 298.39 ms
- Үр дүн: FAIL

Сервер хэвийн ажиллаж байсан ч чанарын шаардлага хангагдаагүй үед k6 автоматаар FAIL төлөв буцаадгийг баталгаажуулсан.

## 5. Ажиллуулах заавар

Dependency суулгаж, сервер ажиллуулах:

```bash
npm install
node server.js
```

Тусдаа терминал дээр туршилтуудыг ажиллуулах:

```bash
# PASS
k6 run slo-test.js

# Chaos
k6 run --duration 2m slo-test.js

# Intentional FAIL
k6 run slo-test-fail.js
```

Chaos туршилтын үед серверийг зогсоож, 10 секунд хүлээгээд дахин асаана.

## 7. Дүгнэлт

Энэхүү лабораториор системийн Performance, Reliability болон Availability чанарын шаардлагыг хэмжигдэхүйц сценарио болгон тодорхойлсон. Сценариог SLO болгон хөрвүүлэхэд хамгийн хэцүү хэсэг нь бодитой тоон босго сонгох байсан. Хэвийн туршилтаар бүх дөрвөн threshold PASS болсон. Chaos туршилтаар Availability 74.54% болж буурсан нь тогтоосон SLO хангагдаагүйг харуулсан. Payment error rate 27.82% болж өссөн. Хүсэлтэд суурилсан Error Budget 254.56% ашиглагдсан. Төлөвлөсөн зогсолтоос урт хугацаанд холболтын алдаа бүртгэгдсэн бөгөөд recovery time-ийг нарийвчлан хэмжээгүй нь туршилтын хязгаарлалт болсон. Report threshold-ийг зориудаар хатууруулахад k6 exit code 99 буцаасан. Цаашид холболтын болон хэрэглээний түвшний алдааг тусад нь хэмжих шаардлагатай. Ингэснээр системийн чанарын шаардлагыг автомат туршилтаар шалгах боломжтойг баталгаажуулсан.
